## Tech stack

One monorepo:

- `apps/api/`: Python backend with FastAPI.
- `apps/web/`: Next.js 16 frontend (App Router, TypeScript, Tailwind CSS 4, `src/` dir). UI components from shadcn/ui (Radix base, added with `pnpm dlx shadcn@latest add <name>` into `src/components/ui/`); icons from lucide-react. Server state with TanStack Query (`QueryClientProvider` in `src/app/providers.tsx`); don't fetch API data in `useEffect`. The web app calls the API at `/api/*` (rewritten to FastAPI in `next.config.ts`) through the typed client in `src/lib/api/`; after changing an API route or model, run `pnpm gen:api` from the root to regenerate `src/lib/api/schema.d.ts`, and commit it. JS deps managed with pnpm workspaces from the repo root (`pnpm-workspace.yaml`, root `pnpm-lock.yaml`); run it with `pnpm dev:web`. Read `apps/web/AGENTS.md` before writing Next.js code: this Next.js version differs from older ones.
- Database: Postgres (ADR-027), accessed from Python with SQLModel (async, asyncpg). Production is hosted Supabase Postgres; dev and tests use local Supabase in Docker (`supabase/config.toml`, started by `scripts/db.sh`), one database per checkout. Schema migrations with Alembic in `apps/api/migrations/`; generate one with `uv run alembic revision --autogenerate -m "<what>"` and read it before committing. The backend owns the schema; the frontend reaches data only through the API.
- Package manager for Python: uv. Add deps with `uv add`, run commands with `uv run`; never use pip, poetry or bare `python`/`venv`. Commit `uv.lock`.

Coding-agent skills live in `.agents/skills/`, with a symlink per skill in `.claude/skills/`. Manage them with the `skills` CLI, never by copying files: `npx skills add <owner/repo> --skill <name> -a universal claude-code -y` to add, `npx skills update` to update, `npx skills install` to restore from `skills-lock.json` (commit it). Use the `fastapi` skill for backend work and the `make-interfaces-feel-better` skill for frontend UI work. Follow `DESIGN.md` (colors, theme, components; ADR-020) for any UI change. The app is self-hosted: ignore its FastAPI Cloud deployment suggestions.

## Rules

Build agents from scratch, with no agent framework (no LangChain, LlamaIndex, CrewAI, Agent SDKs, etc.): the agent loop, tool calling, provider adapters, skills and sessions are our own code. Use pi (MIT, upstream clone at `../pi-upstream`, from https://github.com/earendil-works/pi) and opencode (MIT, clone at `../opencode`, from https://github.com/anomalyco/opencode) and CompanyOS (Elastic License 2.0, clone at `../CompanyOS`, from https://github.com/kortix-ai/CompanyOS) and OpenMausBot (Apache 2.0, clone at `../OpenMausBot`, from https://github.com/milind-soni/OpenMausBot) as the reference designs: read how they do a thing before building ours, then write our own version. Don't vendor or import their packages. Build only what the user asks for, one step at a time.

UX is something we can't compromise on. Every UI change must leave the user knowing what happened and what they can do next: a disabled control says why on hover and focus (a real tooltip, not only a `title`), loading, empty and error states are designed rather than left blank, and nothing flickers or changes state without a visible cue. A feature that works but confuses the user is not done.

Run the app yourself to check a change the user can see in the web app; don't ask the project owner to. Start `pnpm dev:api` and `pnpm dev:web` in the background (they read this worktree's ports from `.worktree.env`), open the web app in the preview, and check the change there before reporting it done. Leave both running and give the URL. Skip this for backend-only, docs or config changes.

Every commit passes the same checks as CI (`.github/workflows/ci.yml`, ADR-010): ruff lint and format, `ty`, pytest, eslint, `tsc`, the API-types check and `next build`. `pnpm check` runs them all; the husky pre-commit hook (`.husky/pre-commit`, installed by `pnpm install`) runs it before every commit and stops the commit on a failure. Fix the failure, never skip the hook (`git commit --no-verify`) unless the project owner says to. A new check goes into both the root `package.json` `check:*` scripts and `ci.yml`, so local and CI stay the same. The hook checks the working tree, not only what is staged, so unrelated uncommitted work can fail it: say so instead of committing around it.

Work on one feature per git worktree (ADR-011): one feature = one branch (`feat/<slug>`, `fix/<slug>`, `chore/<slug>`) = one worktree = one T3 thread. The main checkout stays on `dev` for running the app; don't do feature work there, and don't switch the branch of a worktree you didn't create. A new worktree runs `scripts/worktree-setup.sh` (T3 does it on create): it copies `.env`, installs deps and writes free ports to `.worktree.env`, which `pnpm dev:api`/`pnpm dev:web` read. Never push to `dev`: rebase the branch on `dev`, push it, and open a PR with `gh pr create --base dev` then `gh pr merge --auto --squash --delete-branch`; CI merges it when green. Afterwards remove the worktree. When rebasing, fix Alembic's two heads (point the later migration's `down_revision` at the earlier one) and regenerate generated files (`pnpm gen:api`, `uv lock`, `pnpm install`) instead of merging them by hand.

Comment the code with short one-line comments: every module, class and function gets a one-line docstring (Python) or `//` comment (TypeScript) saying what it does, and a non-obvious block gets a one-line comment before it saying why. Explain intent, not syntax; don't comment lines that already read clearly.

The project owner is new to Python and comes from TypeScript. In Python code, when a construct has a TypeScript counterpart or behaves differently from what a TS developer would expect, add a one-line `# TS:` comment comparing them (e.g. `# TS: like an interface — any class with these members fits, no "implements" needed`). Cover each idiom at its first use in a file, not on every line: Pydantic models (≈ zod schema + type), `Protocol` (≈ interface), `async def` + `yield` (≈ `async function*`), `async with` (≈ `await using`/try-finally), FastAPI `Depends` (≈ dependency injection), decorators, comprehensions (≈ `map`/`filter`), `match`, `:=`, `or` vs `??`.

Learnings live in `.agents/learnings/`, one Markdown file per topic named after the problem (e.g. `python-editor-shows-any.md`). When the user says "add to my learnings" (or similar), write the topic just discussed as a new file there, or update the existing file on that topic, with these sections: **Date**, **Symptom** (what was seen), **Cause** (why it happened, with a TypeScript comparison where it helps), **Fix** (exact steps or config), and **Not a bug** (related behavior that is expected), skipping sections that don't apply. Check `.agents/learnings/` before fixing a problem that looks familiar.

Decisions live in .agents/adr/ as ADRs. Read the ADRs for a feature before changing it. Record each new architectural decision as `ADR-NNN-<slug>.md` (next number in sequence), copied from `.agents/adr/ADR-template.md`. Don't rewrite an accepted ADR; supersede it with a new one and set the old one's status to "Superseded by ADR-XXX".

For every roadmap step or other feature, before writing any code, ask the project owner to predict: state the problem in one or two lines (e.g. "the model sends 3 tool calls and one needs approval: how should they run?") and have them answer in a few sentences, no code. Then show how pi does it and where their answer matched or missed. Skip this step only when they ask.

After every second merged PR, offer a debugging session; run it only if they accept. In it, break one meaningful line on a scratch branch in its own worktree (never on `dev`), run the tests, and show which test fails and its output. They work out what broke and why from the failure, with hints only when they ask. Afterwards restore the line, delete the branch, and confirm the tests pass again.

Track all of this in `.agents/learning-progress.md`: after each prediction or debugging session, add a dated row with the step, the activity, the result and any gaps to revisit, and keep its "PRs merged since the last debugging offer" counter current (increment on each merged PR; reset to 0 when the session is offered). Write it only in the main checkout (`~/Desktop/oss/agentspace/.agents/learning-progress.md`), never in a worktree: every feature appends to the same table, so worktree copies would conflict.
